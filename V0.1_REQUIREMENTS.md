# MootOS Version 0.1 Requirements

**Last reviewed:** July 31, 2026

## Purpose

Version 0.1 is not intended to be a complete AI operating system.

Its purpose is to prove that MootOS can function as a reliable personal AI foundation.

The primary question is:

> Can Moot securely use one ongoing assistant from his phone, keep conversations and important information across deployments, organize information into projects, and continue improving the system without rebuilding it?

## Status legend

- ✅ **Verified** — implemented and manually or automatically verified
- 🟡 **Partial** — useful foundation exists, but the requirement is not complete
- ⬜ **Not implemented** — planned for Version 0.1 but not built yet
- ➡️ **Deferred** — intentionally moved to a later version

A requirement is not complete merely because supporting code exists. The complete user-facing workflow must work.

## Current release summary

Verified foundation:

- Private Railway phone deployment
- Persistent SQLite storage on an attached volume
- Mobile chat interface
- Persistent conversations
- Project organization
- Basic memory CRUD APIs
- Saved memories included in model context
- Replaceable model-provider boundary
- OpenAI provider

Primary incomplete Version 0.1 work:

- Natural-language memory commands
- Memory review and correction UI
- Better memory retrieval
- Basic settings UI
- Readable activity logging
- Explicit tool framework

## Deliverable 1 — Natural conversation

**Status:** 🟡 Partial

Required behavior:

- Understand natural language
- Maintain conversation context
- Understand follow-up questions
- Handle topic changes naturally
- Resolve references such as “that project” or “the other one” when context is sufficient
- Avoid turning every short statement into an unsolicited plan

Implemented:

- Recent conversation history is supplied to the model
- Conversations can be continued across sessions
- A base MootOS identity prompt is supplied
- Project memories can influence responses

Still required:

- Better behavior for notes and status statements
- More reliable reference resolution
- Regression tests for common conversation styles
- Clear behavior when the assistant lacks enough context

Success criterion:

Moot experiences one continuous assistant rather than a sequence of disconnected prompts.

---

## Deliverable 2 — Long-term memory

**Status:** 🟡 Partial

Required behavior:

- Save important memories
- Retrieve memories
- Use relevant memories during conversation
- Distinguish temporary discussion from permanent memory

Implemented:

- Persistent memory table
- Memory creation API
- Memory listing and retrieval APIs
- Project-filtered memories
- Up to 20 recent relevant memories included in model instructions
- Persistence across Railway deployments

Still required:

- Natural decision about what should become permanent
- Explicit remember command
- Better relevance than newest-first retrieval
- Source, confidence, correction, and duplicate handling

---

## Deliverable 3 — Memory management

**Status:** 🟡 Partial

Required user actions:

- Remember information
- Forget information
- Correct information
- Update memories
- View stored memories
- Search stored memories

Implemented:

- Create memory API
- List memory API
- Retrieve memory API
- Delete memory API
- Project filter

Still required:

- “Remember this” conversation command
- “Forget that” conversation command
- “Update that” or correction workflow
- Memory review interface
- Memory edit endpoint or replacement workflow
- Keyword search
- Clear confirmation before sensitive or destructive memory changes

---

## Deliverable 4 — Project organization

**Status:** ✅ Verified foundation

Implemented:

- Five default projects:
  - MootOS
  - Studio
  - Social Media
  - Cars
  - Personal
- Project creation
- Project listing
- Case-insensitive duplicate protection
- Project validation for memories and conversations
- Project-filtered conversation and memory lists
- Project selector in the chat interface

Current limitations:

- No project rename, update, delete, dashboard, goals, tasks, files, or status

Those richer project features belong primarily to Version 0.2.

---

## Deliverable 5 — AI identity

**Status:** 🟡 Partial

Implemented:

- Base instructions identify the assistant as MootOS Version 0.1
- Base instructions describe its core job
- Base instructions require honesty about outside actions

Still required:

- Stronger consistency across different conversation types
- Better documented personal communication preferences
- Clear capability awareness so MootOS does not imply unavailable tools exist

## Deliverable 6 — Mobile interface

**Status:** 🟡 Partial

Implemented and verified:

- Responsive chat page
- User and assistant message bubbles
- Text composer
- Conversation history
- Starting and reopening conversations
- Project selector
- Loading state
- Readable error state
- Login page

## Deliverable 7 — Replaceable AI engine

**Status:** ✅ Verified foundation

Implemented:

- Provider protocol
- Model router
- Normalized model response
- OpenAI provider
- Environment-based provider and model selection
- Fake provider testing
- Provider-side response storage disabled

Current limitation:

- OpenAI is the only implemented provider

Future providers may include local models and additional cloud providers without moving MootOS-owned memory into those providers.

---

## Deliverable 8 — Basic settings

**Status:** ⬜ Not implemented

Originally proposed settings:

- Preferred AI provider
- Local AI enabled or disabled
- Cloud AI enabled or disabled
- Cloud budget
- Permission preferences

Current state:

- Provider and model are configured through environment variables
- There is no settings page or persisted settings model
- Local AI and budget controls do not exist

The first settings UI should remain small and should not claim control over providers that are not implemented.

---

## Deliverable 9 — Logging

**Status:** 🟡 Partial

Implemented:

- Conversations and messages are timestamped
- Assistant messages record provider and model
- Railway supplies deployment logs
- Errors are returned through FastAPI responses

Still required:

- Readable activity log
- Memory change history
- Authentication and tool activity records where appropriate
- Clear error identifiers
- Model latency and usage metadata if approved
- Privacy-aware logging rules

Logs must not expose secrets or unnecessary private content.

---

## Deliverable 10 — Tool framework

**Status:** ⬜ Not implemented

Version 0.1 does not require many tools, but the architecture should eventually support controlled additions such as:

- GitHub
- Calendar
- Email
- File system
- Browser research
- Coding agent

Current state:

- There is no runtime tool registry, permission system, tool-execution record, or approval flow.
- GitHub work is currently performed externally through connected AI tooling, not by the deployed MootOS application.

Do not document external ChatGPT connector abilities as built-in MootOS tools.

## Foundation requirements

These requirements support every user-facing deliverable.

### Secure private deployment

**Status:** ✅ Verified foundation

- Password login
- Signed HTTP-only session
- Secure cookies on Railway
- Protected application and APIs
- Public minimal health endpoint
- Private variables stored in Railway

Future hardening:

- Fail closed when production auth variables are absent
- Login rate limiting
- Stronger password-management workflow

### Persistent production storage

**Status:** ✅ Verified for normal deployments

- Railway volume attached at `/data`
- Production database at `/data/mootos.db`
- Data survived three consecutive deployments

Still required:

- Automatic backups
- Restore testing
- Schema migration runner
- SQLite connection hardening

### Understandable development process

**Status:** ✅ Verified foundation

- Focused branches and pull requests
- Automated tests
- ADRs
- Plain-language review
- Explicit merge approval
- Comprehensive project documentation

## Out of scope for Version 0.1

The following remain deferred:

- Voice conversations
- Camera input
- Real-time screen understanding
- Social media publishing automation
- Email automation
- General computer control
- Financial account access
- Home automation
- Vehicle integrations
- Continuous autonomous background operation
- Multiple autonomous AI agents
- Board-of-directors advisory system
- Automatic self-editing or silent learning
- Multi-user commercial accounts

These ideas may remain on the roadmap without blocking a reliable Version 0.1.

## Definition of done

Version 0.1 is complete when this statement is true:

> Moot can securely open MootOS on his phone, hold a natural ongoing conversation, deliberately save important information, retrieve the right information later, review and correct memories, organize information into projects, and operate the system through deployments without losing data or depending on undocumented steps.

## Recommended completion order

1. Comprehensive documentation
2. Database and production foundation hardening
3. Natural-language memory commands
4. Memory review, correction, and basic search
5. Conversation behavior refinement
6. Basic settings and readable activity logging
7. Version 0.1 release review

Reliability, clarity, privacy, and user control are more important than feature count.
