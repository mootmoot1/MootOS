# MootOS Version 0.1 Requirements

**Last reviewed:** August 1, 2026

## Purpose

Version 0.1 proves that MootOS can function as a reliable personal AI foundation.

Primary question:

> Can Moot securely use one ongoing assistant from his phone, keep conversations and important information across deployments, deliberately save useful facts, organize them into projects, and continue improving the system without rebuilding it?

## Status legend

- ✅ **Verified** — implemented and manually or automatically verified
- 🟡 **Partial** — useful foundation exists, but the complete workflow is unfinished
- ⬜ **Not implemented** — planned but not built
- ➡️ **Deferred** — intentionally moved later

## Current foundation

Implemented and production-verified on `main`:

- Private Railway phone deployment
- Persistent conversations on the `/data` SQLite volume
- Mobile chat interface
- Project organization
- Memory CRUD APIs
- Global and project-focused memory context
- Hardened SQLite connections and versioned migrations
- Railway auth that fails closed
- Replaceable model-provider boundary and OpenAI provider
- Explicit `remember` and `save` commands through normal chat
- Atomic database write and memory confirmation
- Cross-chat recall from SQLite
- Memory persistence through Railway rebuilds
- Protected memory review interface
- All-memory, global-only, and exact-project filters
- Memory content, scope, project, source, and creation date display
- Migration 2 memory lifecycle fields
- UI-selected correction with confirmation
- Atomic append-and-supersede history preservation
- Active-only listings and model context
- Correction-history API
- Corrected active-memory recall after another Railway rebuild

Implemented on the current feature branch, with production verification pending:

- Recoverable memory archive and restore
- Active and Archived views
- Explicit Forget and Restore confirmation dialogs
- Archived-row exclusion from model context
- Hard-delete protection for archived rows

Primary incomplete Version 0.1 work:

- Review, merge, and production verification of recoverable forgetting
- Better retrieval and duplicate handling
- Conversation behavior refinement
- Basic settings and readable activity logging
- Automated encrypted backup, retention, and recurring restore verification

The manual backup and restore procedure has been completed once. The non-private record is in [`docs/BACKUP_RESTORE_VERIFICATION_2026-08-01.md`](docs/BACKUP_RESTORE_VERIFICATION_2026-08-01.md). Automatic backups remain unimplemented.

## Deliverable 2 — Long-term memory

**Status:** 🟡 Partial; deliberate save, durable recall, review, and correction are production-verified; recoverable forgetting is branch-only

Implemented and verified:

- Persistent `memories` table
- Create, list, retrieve, filter, and delete APIs
- Global and project-focused model context
- Up to 20 newest relevant active memories supplied to the model
- Persistence across Railway deployments
- Deterministic commands beginning with `remember`, `save this`, or `save to memory`
- Chat saves use memory type `explicit_chat`
- Explicit saves bypass the external model provider
- Conversation, user message, memory row, and confirmation commit atomically
- Confirmation occurs only after the complete transaction succeeds
- Failed memory or confirmation writes roll back the complete explicit-memory turn
- End-to-end save in one chat and recall in a brand-new chat
- Production save and cross-chat recall
- Recall of saved and corrected active memories after Railway rebuilds
- Protected `GET /memory` review page
- Newest-first active memory cards
- Global and project scope display
- Memory type or source display
- Creation date display
- All-memory, global-only, and exact-project filters
- Safe browser rendering through `textContent`
- Correction history and active-only recall

Still required:

- Production verification of recoverable archive and restore
- Better relevance than newest-first retrieval
- Source and confidence metadata beyond the current type, scope, and timestamp
- Duplicate detection

Implemented on the current forget branch:

- `POST /memories/{id}/restore`

- Per-memory Forget and Restore controls

Next required sequence:

1. Review, merge, and production-verify recoverable forgetting
2. Keyword search and retrieval
3. Conversation behavior refinement

Lifecycle model:

```text
active
superseded
archived
```

Migration 2 is merged, deployed, and documented in ADR-016. The forget branch reuses schema 2 and is documented in ADR-017.

Still required:

- Keyword search
- Duplicate detection
- Natural-language `forget` and `update` commands only after safe selection and confirmation behavior exists
- Permanent deletion or secure erasure only as a separately designed high-risk workflow

## Foundation requirements

### Secure private deployment

**Status:** ✅ Verified foundation

- Password login
- Signed HTTP-only sessions
- Secure Railway cookies
- Protected application and APIs
- Minimal public health endpoint
- Railway startup fails when private auth is missing
- Public Railway startup requires an explicit override

The memory review, correction, history, archive, restore, and listing endpoints all remain inside the existing authenticated boundary.

Still required: login rate limiting and stronger password management.

### Persistent production storage

**Status:** ✅ Hardened and production-verified foundation; one manual recovery drill completed, automation remains incomplete

Implemented and verified:

- Railway volume at `/data`
- Production database at `/data/mootos.db`
- Central database connection layer
- Foreign keys, WAL, busy timeout, and `NORMAL` synchronous mode
- Numbered migrations and schema verification
- Existing-data preservation tests
- Concurrent-write tests
- Post-hardening conversation persistence
- Chat-created memory persistence across Railway rebuilds
- Migration 2 existing-data preservation
- Corrected active-memory persistence through a rebuild

Verified manual safety checkpoint:

- Consistent SQLite online backup from Railway
- Private off-volume transfer
- Matching SHA-256 before and after transfer
- `PRAGMA integrity_check = ok`
- Non-production restore copy opened by MootOS
- Known conversation and memory reads from the restore copy

Still required:

- Production verification of archive and restore persistence
- Automated encrypted backups
- Retention policy
- Scheduled restore verification
- Tested production disaster-recovery procedure

### Understandable development process

**Status:** ✅ Verified foundation

- Focused branches and PRs
- Automated tests
- Plain-language review
- External read-only review when useful
- Explicit merge approval
- Documentation updated with behavior changes

## Definition of done

Version 0.1 is complete when:

> Moot can securely open MootOS on his phone, hold a natural ongoing conversation, deliberately save important information, retrieve it later, review and correct memories, remove outdated memories safely, organize information into projects, and operate through deployments without losing data or depending on undocumented steps.

## Recommended completion order

1. Record PR #12 production verification and backup procedure — complete
2. Memory review interface — complete
3. Memory correction with shared lifecycle migration and preserved history — complete
4. Recoverable memory archival and restoration — current
5. Keyword retrieval before embeddings
6. Conversation behavior refinement
7. Curated Moot bootstrap profile import
8. Basic settings and activity logging
9. Automated backup and recovery completion
10. Version 0.1 release review

The required pre-migration off-volume backup and non-production restore drill were completed on August 1, 2026. Migration 2 and correction are production-verified. Recoverable forgetting still requires exact-head review, explicit merge approval, and post-deployment verification.

Reliability, clarity, privacy, and user control are more important than feature count.
