# MootOS Version 0.1 Requirements

**Last reviewed:** July 31, 2026

## Purpose

Version 0.1 proves that MootOS can function as a reliable personal AI foundation.

Primary question:

> Can Moot securely use one ongoing assistant from his phone, keep conversations and important information across deployments, organize information into projects, and continue improving the system without rebuilding it?

## Status legend

- ✅ **Verified** — implemented and manually or automatically verified
- 🟡 **Partial** — useful foundation exists, but the complete workflow is not finished
- ⬜ **Not implemented** — planned for Version 0.1 but not built
- ➡️ **Deferred** — intentionally moved later

A requirement is not complete merely because supporting code exists. The complete user-facing workflow must work.

## Current release summary

Verified or implemented foundation:

- Private Railway phone deployment
- Persistent SQLite volume at `/data`
- Mobile chat interface
- Persistent conversations
- Project organization
- Basic memory CRUD APIs
- Saved memories included in model context
- Replaceable model-provider boundary
- OpenAI provider
- Centralized SQLite connection policy
- Foreign-key enforcement, WAL, `NORMAL` synchronous mode, and a five-second busy timeout
- Numbered schema migrations and migration history
- Railway auth that fails closed when private variables are missing
- Exact direct dependency pins
- Database and auth hardening tests

Primary incomplete Version 0.1 work:

- Natural-language memory commands
- Memory review and correction UI
- Better memory retrieval
- Conversation behavior refinement
- Basic settings UI
- Readable activity logging
- Explicit tool framework
- Automatic database backup and tested restore

## Deliverable 1 — Natural conversation

**Status:** 🟡 Partial

Required:

- Understand natural language
- Maintain context
- Understand follow-ups
- Handle topic changes
- Resolve references when context is sufficient
- Avoid turning every short statement into an unsolicited plan

Implemented:

- Recent history supplied to the model
- Conversations continue across sessions
- Base MootOS identity instructions
- Project memories influence responses

Still required:

- Better note and status-statement behavior
- More reliable reference resolution
- Regression tests for common conversation styles
- Clear behavior when context is insufficient

## Deliverable 2 — Long-term memory

**Status:** 🟡 Partial

Required:

- Save important memories
- Retrieve memories
- Use relevant memories
- Distinguish temporary discussion from permanent memory

Implemented:

- Persistent memory table
- Memory create, list, retrieve, and delete APIs
- Project-filtered memories
- Up to 20 recent memories in model instructions
- Persistence across Railway deployments
- Hardened SQLite connection policy
- Versioned database migrations

Still required:

- Explicit remember command
- Deliberate choice of what becomes permanent
- Better relevance than newest-first retrieval

## Foundation requirements

### Secure private deployment

**Status:** ✅ Verified foundation, with hardened startup pending Railway smoke verification

Implemented:

- Password login
- Signed HTTP-only sessions
- Secure cookies on Railway
- Protected application and APIs
- Public minimal health endpoint
- Private variables in Railway
- Partial auth configuration rejected
- Railway startup fails when both private auth values are missing
- Public Railway startup requires explicit `MOOTOS_ALLOW_PUBLIC=true`

Still required:

- Login rate limiting
- Stronger password-management workflow

### Persistent production storage

**Status:** 🟡 Hardened in code and automated tests; production upgrade verification required

Implemented:

- Railway volume at `/data`
- Production database at `/data/mootos.db`
- Data survived three deployments before hardening
- Central database connection layer
- Foreign keys enabled per connection
- WAL mode and busy timeout
- `NORMAL` synchronous mode
- Numbered migration runner
- Existing database adoption test
- Newer-schema rejection
- Concurrent-write test

Still required:

- Post-merge Railway smoke test
- Automatic backups
- Restore testing
- Off-volume encrypted backup storage

### Understandable development process

**Status:** ✅ Verified foundation

- Focused branches and PRs
- Automated tests
- ADRs
- Plain-language review
- Explicit merge approval
- Comprehensive documentation
- Documentation updated in the same PR as behavior changes

## Out of scope for Version 0.1

- Voice conversations
- Camera and screen understanding
- Social media publishing automation
- Email automation
- General computer control
- Financial account access
- Home and vehicle integrations
- Continuous autonomous background operation
- Multiple autonomous agents
- Board-of-directors advisory system
- Silent self-editing or learning
- Multi-user commercial accounts

## Definition of done

Version 0.1 is complete when:

> Moot can securely open MootOS on his phone, hold a natural ongoing conversation, deliberately save important information, retrieve the right information later, review and correct memories, organize information into projects, and operate through deployments without losing data or depending on undocumented steps.

## Recommended completion order from this point

1. Review, merge, and verify foundation hardening in Railway
2. Natural-language memory commands
3. Memory review, correction, and keyword search
4. Conversation behavior refinement
5. Curated Moot bootstrap profile import
6. Basic settings and readable activity logging
7. Version 0.1 release review

Reliability, clarity, privacy, and user control are more important than feature count.
