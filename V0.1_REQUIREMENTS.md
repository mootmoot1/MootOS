# MootOS Version 0.1 Requirements

**Last reviewed:** August 8, 2026

## Purpose

Version 0.1 proves that MootOS can function as a reliable private personal-AI foundation with durable state, understandable controls, honest capability boundaries, and a path to future execution/automation without pretending unfinished features exist.

## Complete foundation requirements

- [x] Private phone-accessible Railway deployment
- [x] One-replica persistent SQLite volume
- [x] Fail-closed storage/readiness checks
- [x] Private password + signed session boundary
- [x] Login cooldown and core private HTTP headers
- [x] Mobile chat UI
- [x] Persistent conversations/messages
- [x] Project organization
- [x] Replaceable model-provider interface
- [x] OpenAI Responses API provider
- [x] Atomic provider-backed successful chat persistence
- [x] Sanitized provider/storage failure handling
- [x] Model-input budgeting and capability guidance
- [x] Versioned SQLite migrations and compatibility checks
- [x] WAL, foreign keys, busy timeout, centralized connections
- [x] Manual off-volume backup and isolated restore verification

## Memory requirements

- [x] Durable memory create/list/get
- [x] Explicit chat save commands
- [x] Write-before-confirm atomicity
- [x] Cross-chat recall
- [x] Memory review UI
- [x] Project/global filtering
- [x] Keyword search
- [x] Deterministic concept-aware retrieval without embeddings
- [x] Correction with preserved history
- [x] Recoverable archive/forget
- [x] Restore
- [x] Archived/superseded exclusion from normal recall
- [x] Intelligent explicit chat correction with no-guess ambiguity handling
- [x] Curated private bootstrap-profile preview/import
- [ ] Automatic memory extraction from ordinary chat — intentionally not part of current foundation
- [ ] Embedding/vector retrieval — deferred until simpler retrieval proves inadequate

## Execution/audit foundation

- [x] Durable `runs` schema
- [x] Model Run start/success/failure lifecycle
- [x] Sanitized failure metadata
- [x] Link successful Runs to conversation/user/assistant message IDs
- [x] Keep prompt/response bodies out of Run duplication
- [x] Preserve conceptual boundary between Run and Task

## Task foundation

- [x] Durable Task schema
- [x] Task title/project/status/due-at/lifecycle timestamps
- [x] Timezone-aware Task due timestamp normalized to UTC
- [x] Create/list/get
- [x] Complete/cancel terminal lifecycle
- [x] Project canonicalization
- [x] Authenticated Task APIs
- [x] Explicit chat-driven Task creation
- [x] Atomic Task + chat confirmation turn
- [x] Strict parser that avoids common false positives
- [x] `Remind me ...` remains non-scheduled until a real scheduler exists

## Scheduler/reminder requirement status

Not implemented yet.

A future Scheduler / Reminder v0.1 must not be considered complete until it has, at minimum:

- [ ] durable scheduled state
- [ ] defined user-timezone and UTC semantics
- [ ] restart/offline catch-up behavior
- [ ] duplicate-fire prevention/idempotent claim behavior
- [ ] delivered/failed/cancelled state
- [ ] bounded retry policy if delivery can fail
- [ ] cancellation/rescheduling behavior
- [ ] controlled-time automated tests
- [ ] clear Railway process/worker design
- [ ] production verification of at least one real one-time reminder

Natural-language `Remind me ...` must not be wired to a deterministic write until these delivery semantics exist.

## External tools / approvals

Not implemented in Version 0.1 current code:

- [ ] calendar/email/messaging integrations
- [ ] write-capable external tools
- [ ] frozen operation records
- [ ] approval UI/policy engine
- [ ] autonomous execution

Task remains intention rather than permission. Future external writes must use explicit execution/audit/approval boundaries rather than reading mutable Task fields and acting directly.

## Version 0.1 current completion view

The original personal-foundation goal is largely achieved: MootOS can chat, persist, remember, review/correct/archive/restore memory, import a curated profile, record model execution metadata, and manage durable Tasks.

The repository is now crossing from **reliable personal foundation** into **time-based execution/notification design**. Scheduler work should therefore be treated as a new reliability boundary, not as a small cosmetic extension of Task `due_at`.

## Quality gates

Meaningful changes should continue to use:

1. focused branch/PR
2. automated tests
3. Python 3.9/3.10/3.11 CI where applicable
4. internal review
5. independent read-only review for significant behavior
6. explicit merge approval
7. controlled Railway deployment
8. production verification for runtime/user-facing changes
9. synchronized current documentation
