# V0.4C Offline PR Preparation and Audit Trust Boundaries

V0.4C is an offline, non-executing architecture. It transforms an existing
authoritative capability-build handoff into a proposed PR package, renders it,
records bounded human input, authorizes and prepares one exact inert action,
and records a structurally validated external result claim. It never calls Git
or GitHub.

`Authoritative` in this milestone means internally reconstructed and checked
against model invariants. It does not mean cryptographically signed, externally
attested, or authenticated.

## Complete chain

1. The V0.4B workflow and handoff record the ordered offline build state and
   sanitized human-review handoff.
2. `PRPackageProposal` represents bounded proposal metadata without approval or
   publication authority.
3. `WorkflowPRPackageCreation` reconstructs that proposal from the exact
   authoritative handoff and does not advance workflow state.
4. `PRPackageRendering` deterministically renders the proposal as Markdown.
5. `WorkflowPRPackageRendering` binds the rendering to its package and preserves
   ready, blocked/inspection-only, and not-rendered dispositions.
6. `WorkflowPRReviewPending` advances only the existing
   `human_decision_pending` step and exposes disposition-appropriate choices.
7. `PRReviewDecisionInput` represents bounded human-supplied input. It does not
   prove the reviewer, source, or choice is authoritative.
8. `WorkflowPRDecisionRecording` mechanically binds an allowed choice to the
   exact pending review. Only a valid `approve_for_pr` becomes eligible for a
   separate publication authorization.
9. `PRPublicationAuthorization` binds explicit authorization metadata to one
   exact repository/base/head/title/body scope. It prepares or executes nothing.
10. `PRPublicationAction` is an inert executor-neutral envelope for that exact
    authorized `create_pull_request` operation.
11. `PRPublicationResult` records a bounded external result claim bound to the
    action. It neither performs nor independently verifies the reported action.

Every stage fails closed when its source type, ordered workflow state,
disposition, decision option, identity, digest, or exact publication scope
cannot be reconstructed. No stage silently repairs a mismatch.

## Exact terminology

- **`workflow complete`** means the defined offline workflow step list is
  exhausted at `human_decision_pending`. It does not mean a decision was
  recorded or PR publication completed.
- **`approve_for_pr`** is an allowed human review decision for an exact review
  chain. It does not itself authorize publication.
- **`authorized`** means the exact Slice 8 publication scope passed its internal
  authorization contract. It does not mean the supplied authorizer identity was
  externally authenticated, an action was prepared, or execution occurred.
- **`action_prepared`** means an inert executor-neutral action envelope exists.
  It does not mean GitHub was contacted or accepted an operation.
- **`pr_created`** means a structurally valid external claim reported PR
  creation for the bound action. It does not mean V0.4C independently verified
  GitHub state, that the PR remains open, or that it was merged.
- **`externally_verified`** remains `false` throughout V0.4C.

## Identity, verification, and replay limits

Reviewer, authorizer, and reporter identities are supplied labels. V0.4C does
not authenticate them through credentials, signatures, sessions, or an
external identity provider. Title and rendered-body SHA-256 digests bind exact
content but do not authenticate the actor supplying an authorization or result.

The Slice 9 idempotency key is a deterministic identity for exact action scope.
Identical authorized scope can produce the same key. V0.4C has no persistence,
uniqueness registry, durable deduplication, retry protocol, or replay protection.

The result receipt distinguishes an external report, an externally reported
attempt, and an externally reported success. None is independently verified
truth. Authentication, GitHub verification, credential ownership, execution,
retries, uncertain-outcome reconciliation, and persistent audit storage require
separate future architecture decisions.

## Authority boundary

V0.4C can represent and validate offline state. It cannot access Git, GitHub,
the network, credentials, backend runtime, or the tool registry; launch
subprocesses; create branches, commits, or PRs; push, merge, deploy, retry, or
dispatch workers. It grants no autonomous merge or deployment authority.
