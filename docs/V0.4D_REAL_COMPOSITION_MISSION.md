# V0.4D Real Composition Mission

V0.4D proves one bounded user goal by composing existing registered tools. It
does not add a mission-specific tool, another registry, or another executor.
ADR-040 is the normative decision record.

## Proven mission

> Review current project activity and task status, consult relevant stored
> context, then prepare one appropriate follow-up task for human approval.

The immutable proposal describes five steps. Feasibility binding resolves all
authority-relevant facts from the supplied live Tool Registry. The runtime then
uses the existing central executor for four reads:

1. `projects.overview`
2. `tasks.status_summary`
3. `tasks.list`
4. `memory.search`

The project with the greatest `open_tasks` count is selected; ties use its NFC,
trimmed, case-folded name and then the exact name for a stable final tie-break.
The summary's open count must equal the bounded open Task set returned by
`tasks.list`. A mismatch stops the mission.

The fifth request is an exact `tasks.create` call. It is schema-validated and
stored through the existing frozen pending-operation mechanism. It is not sent
to the tool executor and no Task exists before separate human approval.

## Binding and revalidation

The proposal permits only approved literals and declared result bindings with
a closed transform set. Tool output is data only and cannot select tools,
schemas, risks, executors, steps, budgets, or approval.

The feasibility plan binds each exact tool name, version, risk, input-schema
digest, capability set, and dependency set into one registry snapshot digest.
The runtime recomputes and compares the complete plan immediately before every
request. A change blocks the remaining mission; it is never silently replanned.

Actual result fields are checked for presence, type, size, and baseline-specific
consistency before dependent arguments are materialized. Runtime metadata keeps
only digests, Run IDs, bounded counts, and the selected project—not unrestricted
tool output.

## Budget and status

One in-memory budget covers all five processed requests. The limits are five
processed requests, two identical request signatures, and two consecutive
failures. The frozen write consumes request five through the distinct
`pending_operation` outcome, which does not falsely claim either execution or
failure. There are no retries and no cross-process budget continuity.

Mission status comes from execution and durable operation state:

- `approval_pending`: four reads succeeded and the exact write is frozen;
- `completed`: the existing approval system independently executed that write;
- `rejected`, `failed`, or `expired`: the durable operation reached that state;
- `blocked` or `failed`: planning/runtime invariants prevented continuation;
- `running`: the separately approved operation is currently claimed.

Model narration cannot set status.

## Receipt and authority

The immutable bounded receipt binds the mission/goal/plan/registry identities,
ordered tool and schema/risk facts, request signatures, derived data-flow
counts, successful read Run IDs, pending-operation identity, and any terminal
write Run/reference. Receipt construction only reads existing Run and operation
records; it cannot approve or execute.

V0.4D gains authority only to coordinate existing `read_only` tools and prepare
one existing `internal_write` pending operation. It gains no automatic approval,
high-risk execution, new credentials, shell/filesystem/network authority,
dynamic registration, background mission, persistent mission workflow,
generalized resume, GitHub action, merge, deployment, or Continuous Builder
authority.

The mission plan and budget are in memory. The operation and Runs use existing
durable storage, but V0.4D adds no mission persistence or durable replay system.
Request signatures identify exact calls only; they do not guarantee uniqueness
across processes.

## Verification boundary

The end-to-end proof uses the real registry and executor, confirms data from
earlier reads determines later arguments, confirms no Task exists at the pending
boundary, and separately exercises the existing approve and reject flows. This
is local architectural verification. It is not deployment verification and
does not require or claim Railway availability.
